# 面向 CHI 的简洁埋点指标方案

## 说明

这份文档只保留最适合当前原型的核心 quantitative metrics，并用最简洁的方式说明：

1. `指标是什么`
2. `怎么定义`
3. `为什么值得收`

原则是：

- 尽量使用当前原型已经支持的数据
- 尽量让 reviewer 一眼能理解
- 尽量避免过度依赖任务类型差异很大的指标
- 优先保留能说明 scaffold 是否被接受、是否被使用、是否带来即时帮助的指标

---

## Primary Metrics

### 1. 第一步建议使用率

**定义**  
用户使用 AI 第一建议开始任务的次数 / 第一建议出现的次数

**原因**  
这是最直接的启动阶段 scaffold engagement 指标。它不需要复杂解释，能直接说明用户是否愿意接受 AI 给出的第一步支持。

### 2. 卡住求助触发率

**定义**  
用户主动触发卡住求助的次数 / 卡住总次数

**原因**  
这是最直接的执行阶段 scaffold engagement 指标。它能说明用户在真正卡住的时候，会不会想到使用这个支持功能。

### 3. 反思完成率

**定义**  
完整走到反思结尾的次数 / 打开反思的次数

**原因**  
这能直接说明反思环节是否可完成、是否不会因为负担过高而中途放弃。对于反思类 scaffold，这是最关键的可持续性指标。

### 4. scaffold 后即时主观改善

**定义**  
在关键 scaffold 后，用户对“是否更清楚下一步 / 是否更贴近实际情况 / 是否更理解自己问题”的轻量评分

**原因**  
这是当前原型里最贴近“元认知支持”本身的指标。相比单纯看时间差，这个指标更能说明 scaffold 是否让用户在当下感到更清楚、更被接住。

### 5. 任务时长

**定义**  
一天内累计的任务 session 总时长

**原因**  
这是最直观的任务投入指标之一。虽然不能单独解释为 scaffold 的作用，但适合作为长期趋势中的辅助结果。

### 6. 电脑使用时长

**定义**  
一天内累计的电脑活跃使用时长

**原因**  
这是最直观的被动感知指标之一。它本身不等于任务投入，但与任务时长一起看时，可以帮助判断用户的一天是否主要围绕明确任务展开。

---

## Secondary Metrics

### 7. 第一步建议跳过率

**定义**  
用户跳过 AI 第一建议直接开始的次数 / 第一建议出现的次数

**原因**  
这个指标与第一步建议使用率互补。它可以帮助判断：建议是否不合适、时机是否不对，或者用户是否根本不觉得这个 scaffold 有必要。

### 8. 求助后继续执行率

**定义**  
用户在求助后是否重新进入任务执行状态的比例

**原因**  
它比单纯“有没有点求助”更进一步，能反映 stuck scaffold 是否真的帮助用户回到任务执行，而不只是打开了一个界面。

### 9. 每日任务完成率

**定义**  
当日完成任务数 / 当日任务总数

**原因**  
这是最容易理解的任务结果指标。虽然受任务内容和难度影响较大，但仍适合作为同一参与者跨天趋势中的辅助结果。

### 10. 每日卡住次数

**定义**  
每天发生的卡住事件总数

**原因**  
这个指标能反映每天执行过程中的摩擦程度。它不直接说明 scaffold 的效果，但适合用来观察长期使用后是否出现更顺畅的执行过程。

### 11. 反思打开率

**定义**  
打开反思的天数 / 活跃使用天数

**原因**  
这个指标能说明用户是否认为反思值得进入。如果打开率很低，往往意味着反思环节的负担、时机或价值感存在问题。

### 12. 任务时长 / 电脑使用时长

**定义**  
一天内任务时长占电脑使用时长的比例

**原因**  
这个比例比单看电脑使用时长更有意义，因为它更接近“有多少电脑使用是围绕明确任务展开的”。这对 ADHD 任务管理场景尤其重要。

---

## Exploratory Metrics

### 13. 反思平均回复字数

**定义**  
每次反思中用户消息的平均字符数

**原因**  
它可以作为反思投入程度的弱代理指标，但不应直接被解释为元认知能力提升。因此更适合放在 exploratory 层。

### 14. 反思对话轮数

**定义**  
每次反思中用户参与的轮次数

**原因**  
它是另一个简单的参与度指标，但同样不能直接等同于反思质量或元认知深度，因此适合作为补充观察。

### 15. 次日闭环效应

**定义**  
完成反思后，次日是否更可能使用第一建议、打开反思或主动求助

**原因**  
这个指标可以帮助探索反思是否对后续行为产生影响，但因为中间会受到很多外部因素影响，所以更适合作为 exploratory analysis。

### 16. 卡住后结果分类

**定义**  
卡住后回到原任务、切到其他任务、当天不再继续等行为分类

**原因**  
这个指标有助于展示 stuck support 之后的行为走向，但它更适合作为补充分析，而不是核心结果。

---

## 最终推荐

如果只保留一组最现实、最稳、最容易让 CHI reviewer 理解的指标，建议优先采用：

### Primary

1. `第一步建议使用率`
2. `卡住求助触发率`
3. `反思完成率`
4. `scaffold 后即时主观改善`
5. `任务时长`
6. `电脑使用时长`

### Secondary

7. `第一步建议跳过率`
8. `求助后继续执行率`
9. `每日任务完成率`
10. `每日卡住次数`
11. `反思打开率`
12. `任务时长 / 电脑使用时长`

### Exploratory

13. `反思平均回复字数`
14. `反思对话轮数`
15. `次日闭环效应`
16. `卡住后结果分类`
# 面向 CHI 的研究问题与埋点方案

## 文档目的

这份文档用于整理当前原型最适合收集的定量数据。目标不是“尽可能多地记录”，而是保留一组 **直观、可解释、并且与当前原型高度匹配** 的指标，让 reviewer 能快速理解：

- scaffold 有没有真正被用起来
- scaffold 有没有带来当下可观察的变化
- 用户是否随着使用逐渐形成更稳定的任务管理行为

当前原型包含三个阶段：

1. `启动阶段`：启动第一步
2. `执行阶段`：任务过程中卡住求助
3. `反思阶段`：数据可视化支持的反思

---

## 选择指标的原则

本方案优先保留以下类型的数据：

- **当前原型已经支持**，或只需要非常轻量的新增埋点
- **reviewer 一眼能理解**
- **与任务类型关系较弱**，更适合同一参与者的纵向比较
- **直接对应 scaffold 的使用、接受和即时影响**
- **尽量基于时长、次数、比例等直观量化结果**

本方案不把下面这些内容作为当前版本的核心定量指标：

- 预估时长准确度
- 任务拆解质量
- 优先级设置质量
- 深度语义编码后的“元认知能力得分”
- 过度依赖小时占比推导出的复杂指标

原因是：这些指标要么当前原型并不直接支持，要么解释成本较高，不够直观。

---

## 核心逻辑

当前原型最适合 CHI 的 quantitative story 不是：

`AI 出现 -> 时间一定缩短`

而是：

`AI 出现 -> 用户是否接受 -> 用户是否继续行动 -> 是否形成更稳定的任务投入与反思完成`

因此，建议把指标分为三层：

1. `Primary metrics`：最核心、最稳的指标
2. `Secondary metrics`：辅助说明 scaffold 如何发挥作用
3. `Exploratory metrics`：可以保留，但解释时更谨慎

---

## Primary Metrics

这些指标最适合作为主要 quantitative evidence。

| 指标 | 阶段 | 定义 | 为什么重要 |
|---|---|---|---|
| `第一步建议使用率` | 启动 | 用户使用 AI 第一建议开始任务的次数 / 第一建议出现的次数 | 直接反映启动 scaffold 是否被接受 |
| `卡住求助触发率` | 执行 | 用户主动触发卡住求助的次数 / 卡住总次数 | 直接反映用户在真正需要帮助时，会不会想到使用 scaffold |
| `反思完成率` | 反思 | 完整走到反思结尾的次数 / 打开反思的次数 | 直接反映反思环节是否可完成、是否不会被中途放弃 |
| `scaffold 后即时主观改善` | 三阶段 | 在关键 scaffold 之后，用户对“是否更清楚下一步 / 是否更贴近实际情况 / 是否更理解自己问题”的轻量自评 | 这是当前原型最贴近“元认知支持”本身的指标 |
| `任务时长` | 执行 | 一天内累计的任务 session 总时长 | 是最直观的任务投入指标之一 |
| `电脑使用时长` | 执行 | 一天内累计的电脑活跃时长 | 是最直观的被动感知使用指标之一 |

---

## Secondary Metrics

这些指标用于辅助解释 scaffold 的使用与效果。

| 指标 | 阶段 | 定义 | 为什么重要 |
|---|---|---|---|
| `第一步建议跳过率` | 启动 | 用户跳过 AI 第一建议直接开始的次数 / 第一建议出现的次数 | 与使用率互补，可帮助判断建议是否不合适或不必要 |
| `求助后继续执行率` | 执行 | 用户在求助后是否重新进入任务执行状态的比例 | 比“有没有点求助”更接近 scaffold 的即时行为结果 |
| `每日任务完成率` | 执行 | 当日完成任务数 / 当日任务总数 | 最直观的任务结果指标，适合作为辅助结果 |
| `每日卡住次数` | 执行 | 每天发生的卡住事件总数 | 反映每天执行过程中的摩擦程度 |
| `反思打开率` | 反思 | 打开反思的天数 / 活跃使用天数 | 反映用户是否认为反思值得进入 |
| `任务时长 / 电脑使用时长` | 执行 | 一天内任务时长占电脑使用时长的比例 | 用一个简单比例刻画“有多少电脑使用围绕明确任务展开” |

## Exploratory Metrics

这些指标可以保留，但不建议作为最核心的定量结论。

| 指标 | 阶段 | 定义 | 为什么重要 |
|---|---|---|---|
| `反思平均回复字数` | 反思 | 每次反思中用户消息的平均字符数 | 可作为反思投入程度的弱代理指标，但不能直接等同于元认知能力 |
| `反思对话轮数` | 反思 | 每次反思中用户参与的轮次数 | 另一个简单的参与度代理指标 |
| `次日闭环效应` | 跨天 | 完成反思后，次日是否更可能使用第一建议、打开反思或主动求助 | 可用于探索反思是否影响后续行为，但应谨慎解释 |
| `卡住后结果分类` | 执行 | 卡住后回到原任务、切到其他任务、当天不再继续等 | 有助于展示 stuck support 之后的行为走向，但更适合作为补充分析 |

## 基于现有监控数据可直接构建的时长指标

当前原型已经具备两类核心时长数据：

1. `电脑使用时长`
   - 来自 activity records
   - 表示一天内用户处于“活跃使用”状态的累计时长

2. `任务时长`
   - 来自 task session / tracker events
   - 表示一天内用户处于明确任务执行状态的累计时长

基于这两类时长，最值得保留的简单指标有：

### 1. 总电脑使用时长

用于描述一天整体的电脑活跃程度。

### 2. 总任务时长

用于描述一天围绕明确任务的投入量。

### 3. 任务时长占电脑使用时长的比例

定义：

`任务时长 / 电脑使用时长`

这个比例比单看“总电脑使用时长”更有意义，因为它更接近：

- 用户的电脑使用有多少真正围绕明确任务展开

### 4. 卡住前任务时长 / 卡住后任务时长

如果后续要分析 stuck support 的即时影响，可以对单次或单日做简单比较：

- 卡住前已经投入了多久
- 求助后是否还有新的任务时长出现

这比单纯看“恢复用了多少秒”更稳，因为它不强行把时间差解释为 scaffold 作用，而是看 **求助之后是否还存在真实任务投入**。

---

## 建议新增的最小埋点事件

为了支持上述指标，只需要增加一小组轻量事件。

| 事件名 | 触发时机 | 字段 |
|---|---|---|
| `firstStep.shown` | AI 第一建议被展示时 | `taskId`, `suggestions[]`, `timestamp` |
| `firstStep.used` | 用户点击某条第一建议并开始时 | `taskId`, `suggestionText`, `timestamp` |
| `firstStep.skipped` | 用户跳过第一建议直接开始时 | `taskId`, `timestamp` |
| `stuck.opened` | 用户打开卡住求助入口时 | `taskId`, `timestamp` |
| `stuck.resumed` | 用户在求助后重新进入执行状态时 | `taskId`, `resumeTaskId`, `timestamp` |
| `reflection.opened` | 用户打开日反思时 | `date`, `timestamp` |
| `reflection.completed` | 用户完成反思流程时 | `date`, `stepCount`, `userTurnCount`, `timestamp` |
| `scaffold.feedback` | 用户在关键 scaffold 后完成轻量主观反馈时 | `phase`, `promptType`, `rating`, `timestamp` |

说明：

- 现有的 `session.started`、`session.ended`、卡住相关 tracker events 仍然可以继续复用
- 现有的 activity records 仍然可以继续复用，用于计算电脑使用时长
- 新增事件主要用于补足“scaffold 是否出现、是否被接受、是否带来即时主观改善”这一层

---

## 建议增加的即时轻量反馈

如果希望更贴近“元认知支持”而不是只看行为结果，最值得增加的是非常轻的即时反馈。

### 启动阶段

在第一步建议后，轻量询问一次：

- `现在更容易开始了吗？`

可选项：

- `没有`
- `有一点`
- `是`

### 执行阶段

在卡住求助后，轻量询问一次：

- `现在更清楚下一步了吗？`
- `这个建议贴近你的情况吗？`

可选项：

- `没有 / 不贴近`
- `有一点 / 一般`
- `是 / 很贴近`

### 反思阶段

在反思完成后，轻量询问一次：

- `这次反思有帮你更理解今天为什么会卡住吗？`
- `你现在有没有一个比较明确的明天调整点？`

可选项：

- `没有`
- `有一点`
- `有`

这些反馈的价值在于：

- 比时间差更贴近你的研究主题
- 更容易解释为“最近端的元认知变化”
- 能和访谈内容形成更好的互证

## 与研究问题的对应关系

## RQ1

**RQ1. ADHD 大学生在任务规划中会遇到哪些元认知挑战？**

当前原型最适合提供的定量锚点：

- `每日卡住次数`
- `反思打开率`
- `反思完成率`
- `任务时长`
- `电脑使用时长`

说明：

- 如果每日卡住次数较高，说明执行过程中的自我调节困难频繁出现
- 如果反思经常不打开或中途退出，说明元认知支持本身可能负担过高
- 如果电脑使用时长较高，但任务时长较低，也可能说明用户存在“活跃但未围绕明确任务”的情况

对于 RQ1，日志更适合作为 **behavioral anchors**。真正的挑战类型仍然应主要依赖：

- 访谈
- 反思文本
- 个案分析

---

## RQ2

**RQ2. GenAI-powered metacognitive scaffold 如何影响用户的任务规划与执行过程？**

当前原型最适合提供的定量指标：

- `第一步建议使用率`
- `第一步建议跳过率`
- `卡住求助触发率`
- `求助后继续执行率`
- `scaffold 后即时主观改善`

说明：

- 这些指标直接对应 scaffold 是否在关键时刻被使用
- 也直接对应 scaffold 是否让用户感觉“更清楚了”“更贴近了”“更知道下一步了”

这是当前原型最适合由日志强支撑的研究问题。

---

## RQ3

**RQ3. 持续使用该 scaffold 后，用户的任务管理行为与相关元认知表现是否发生变化？**

当前原型最适合提供的纵向指标：

- `第一步建议使用率` 的跨天变化
- `卡住求助触发率` 的跨天变化
- `反思完成率` 的跨天变化
- `任务时长` 的跨天变化
- `每日任务完成率` 的跨天变化
- `每日卡住次数` 的跨天变化

补充的探索性指标：

- `反思平均回复字数`
- `反思对话轮数`
- `次日闭环效应`

说明：

- 这些指标适合做 **within-subject longitudinal analysis**
- 它们更适合回答“同一个人是否逐渐更愿意使用 scaffold，是否逐渐形成更稳定的任务管理行为”
- 不建议把这些指标用于不同参与者之间的直接比较，因为任务类型与情境差异太大

---

## 推荐的展示结构

如果后续需要在论文或汇报中展示，最适合当前原型的结构是：

### 1. 启动链

`第一步建议出现 -> 第一建议使用率 / 跳过率 -> 即时主观改善`

### 2. 执行链

`发生卡住 -> 卡住求助触发率 -> 求助后继续执行率 -> 即时主观改善`

### 3. 任务投入链

`电脑使用时长 -> 任务时长 -> 任务时长 / 电脑使用时长`

### 4. 反思链

`反思打开率 -> 反思完成率 -> 即时主观改善 -> 次日闭环效应`

这样更容易让 reviewer 看出：

- scaffold 有没有进入真实流程
- scaffold 有没有在当下产生“可感知”的支持
- 用户的一天中，有多少投入真正围绕明确任务展开
- scaffold 是否可能对后续行为产生影响

---

## 最终建议

如果只保留一组最现实、最稳、最容易让 CHI reviewer 理解的定量指标，建议优先采用：

### Primary

1. `第一步建议使用率`
2. `卡住求助触发率`
3. `反思完成率`
4. `scaffold 后即时主观改善`
5. `任务时长`
6. `电脑使用时长`

### Secondary

7. `第一步建议跳过率`
8. `求助后继续执行率`
9. `每日任务完成率`
10. `每日卡住次数`
11. `反思打开率`
12. `任务时长 / 电脑使用时长`

### Exploratory

13. `反思平均回复字数`
14. `反思对话轮数`

这组指标的优点是：

- 当前原型基本都能支持

- 更贴近“元认知 scaffold 是否被接受和理解”

# 面向 CHI 的研究问题与埋点方案

## 文档目的

这份文档用于整理当前原型最适合收集的定量数据。目标不是“尽可能多地记录”，而是保留一组 **直观、可解释、并且与当前原型高度匹配** 的指标，让 reviewer 能快速理解：

- scaffold 有没有真正被用起来
- scaffold 有没有带来当下可观察的变化
- 用户是否随着使用逐渐形成更稳定的任务管理行为

当前原型包含三个阶段：

1. `启动阶段`：启动第一步
2. `执行阶段`：任务过程中卡住求助
3. `反思阶段`：数据可视化支持的反思

---

## 选择指标的原则

本方案优先保留以下类型的数据：

- **当前原型已经支持**，或只需要非常轻量的新增埋点
- **reviewer 一眼能理解**
- **与任务类型关系较弱**，更适合同一参与者的纵向比较
- **直接对应 scaffold 的使用、接受和即时影响**

本方案不把下面这些内容作为当前版本的核心定量指标：

- 启动延迟
- 卡住后恢复时间
- 预估时长准确度
- 任务拆解质量
- 优先级设置质量
- 深度语义编码后的“元认知能力得分”

原因是：这些指标要么当前原型并不直接支持，要么受任务性质和情境影响太大，难以稳定归因到 scaffold 本身。

---

## 核心逻辑

当前原型最适合 CHI 的 quantitative story 不是：

`AI 出现 -> 时间变短`

而是：

`AI 出现 -> 用户是否接受 -> 用户是否觉得更清楚 -> 是否继续参与 / 继续行动`

因此，建议把指标分为三层：

1. `Primary metrics`：最核心、最稳的指标
2. `Secondary metrics`：辅助说明 scaffold 如何发挥作用
3. `Exploratory metrics`：可以保留，但解释时更谨慎

---

## Primary Metrics

这些指标最适合作为主要 quantitative evidence。

| 指标 | 阶段 | 定义 | 为什么重要 |
|---|---|---|---|
| `第一步建议使用率` | 启动 | 用户使用 AI 第一建议开始任务的次数 / 第一建议出现的次数 | 直接反映启动 scaffold 是否被接受 |
| `卡住求助触发率` | 执行 | 用户主动触发卡住求助的次数 / 卡住总次数 | 直接反映用户在真正需要帮助时，会不会想到使用 scaffold |
| `反思完成率` | 反思 | 完整走到反思结尾的次数 / 打开反思的次数 | 直接反映反思环节是否可完成、是否不会被中途放弃 |
| `scaffold 后即时主观改善` | 三阶段 | 在关键 scaffold 之后，用户对“是否更清楚下一步 / 是否更贴近实际情况 / 是否更理解自己问题”的轻量自评 | 这是当前原型最贴近“元认知支持”本身的指标 |

---

## Secondary Metrics

这些指标用于辅助解释 scaffold 的使用与效果。

| 指标 | 阶段 | 定义 | 为什么重要 |
|---|---|---|---|
| `第一步建议跳过率` | 启动 | 用户跳过 AI 第一建议直接开始的次数 / 第一建议出现的次数 | 与使用率互补，可帮助判断建议是否不合适或不必要 |
| `求助后继续执行率` | 执行 | 用户在求助后是否重新进入任务执行状态的比例 | 比“有没有点求助”更接近 scaffold 的即时行为结果 |
| `每日任务完成率` | 执行 | 当日完成任务数 / 当日任务总数 | 最直观的任务结果指标，适合作为辅助结果 |
| `每日卡住次数` | 执行 | 每天发生的卡住事件总数 | 反映每天执行过程中的摩擦程度 |
| `反思打开率` | 反思 | 打开反思的天数 / 活跃使用天数 | 反映用户是否认为反思值得进入 |

---

## Exploratory Metrics

这些指标可以保留，但不建议作为最核心的定量结论。

| 指标 | 阶段 | 定义 | 为什么重要 |
|---|---|---|---|
| `反思平均回复字数` | 反思 | 每次反思中用户消息的平均字符数 | 可作为反思投入程度的弱代理指标，但不能直接等同于元认知能力 |
| `反思对话轮数` | 反思 | 每次反思中用户参与的轮次数 | 另一个简单的参与度代理指标 |
| `次日闭环效应` | 跨天 | 完成反思后，次日是否更可能使用第一建议、打开反思或主动求助 | 可用于探索反思是否影响后续行为，但应谨慎解释 |

---

## 建议新增的最小埋点事件

为了支持上述指标，只需要增加一小组轻量事件。

| 事件名 | 触发时机 | 字段 |
|---|---|---|
| `firstStep.shown` | AI 第一建议被展示时 | `taskId`, `suggestions[]`, `timestamp` |
| `firstStep.used` | 用户点击某条第一建议并开始时 | `taskId`, `suggestionText`, `timestamp` |
| `firstStep.skipped` | 用户跳过第一建议直接开始时 | `taskId`, `timestamp` |
| `stuck.opened` | 用户打开卡住求助入口时 | `taskId`, `timestamp` |
| `stuck.resumed` | 用户在求助后重新进入执行状态时 | `taskId`, `resumeTaskId`, `timestamp` |
| `reflection.opened` | 用户打开日反思时 | `date`, `timestamp` |
| `reflection.completed` | 用户完成反思流程时 | `date`, `stepCount`, `userTurnCount`, `timestamp` |
| `scaffold.feedback` | 用户在关键 scaffold 后完成轻量主观反馈时 | `phase`, `promptType`, `rating`, `timestamp` |

说明：

- 现有的 `session.started`、`session.ended`、卡住相关 tracker events 仍然可以继续复用
- 新增事件主要用于补足“scaffold 是否出现、是否被接受、是否带来即时主观改善”这一层

---

## 建议增加的即时轻量反馈

如果希望更贴近“元认知支持”而不是只看行为结果，最值得增加的是非常轻的即时反馈。

### 启动阶段

在第一步建议后，轻量询问一次：

- `现在更容易开始了吗？`

可选项：

- `没有`
- `有一点`
- `是`

### 执行阶段

在卡住求助后，轻量询问一次：

- `现在更清楚下一步了吗？`
- `这个建议贴近你的情况吗？`

可选项：

- `没有 / 不贴近`
- `有一点 / 一般`
- `是 / 很贴近`

### 反思阶段

在反思完成后，轻量询问一次：

- `这次反思有帮你更理解今天为什么会卡住吗？`
- `你现在有没有一个比较明确的明天调整点？`

可选项：

- `没有`
- `有一点`
- `有`

这些反馈的价值在于：

- 比时间差更贴近你的研究主题
- 更容易解释为“最近端的元认知变化”
- 能和访谈内容形成更好的互证

---

## 与研究问题的对应关系

## RQ1

**RQ1. ADHD 大学生在任务规划中会遇到哪些元认知挑战？**

当前原型最适合提供的定量锚点：

- `每日卡住次数`
- `反思打开率`
- `反思完成率`

说明：

- 如果每日卡住次数较高，说明执行过程中的自我调节困难频繁出现
- 如果反思经常不打开或中途退出，说明元认知支持本身可能负担过高

对于 RQ1，日志更适合作为 **behavioral anchors**。真正的挑战类型仍然应主要依赖：

- 访谈
- 反思文本
- 个案分析

---

## RQ2

**RQ2. GenAI-powered metacognitive scaffold 如何影响用户的任务规划与执行过程？**

当前原型最适合提供的定量指标：

- `第一步建议使用率`
- `第一步建议跳过率`
- `卡住求助触发率`
- `求助后继续执行率`
- `scaffold 后即时主观改善`

说明：

- 这些指标直接对应 scaffold 是否在关键时刻被使用
- 也直接对应 scaffold 是否让用户感觉“更清楚了”“更贴近了”“更知道下一步了”

这是当前原型最适合由日志强支撑的研究问题。

---

## RQ3

**RQ3. 持续使用该 scaffold 后，用户的任务管理行为与相关元认知表现是否发生变化？**

当前原型最适合提供的纵向指标：

- `第一步建议使用率` 的跨天变化
- `卡住求助触发率` 的跨天变化
- `反思完成率` 的跨天变化
- `每日任务完成率` 的跨天变化
- `每日卡住次数` 的跨天变化

补充的探索性指标：

- `反思平均回复字数`
- `反思对话轮数`
- `次日闭环效应`

说明：

- 这些指标适合做 **within-subject longitudinal analysis**
- 它们更适合回答“同一个人是否逐渐更愿意使用 scaffold，是否逐渐形成更稳定的任务管理行为”
- 不建议把这些指标用于不同参与者之间的直接比较，因为任务类型与情境差异太大

---

## 推荐的展示结构

如果后续需要在论文或汇报中展示，最适合当前原型的结构是：

### 1. 启动链

`第一步建议出现 -> 第一建议使用率 / 跳过率 -> 即时主观改善`

### 2. 执行链

`发生卡住 -> 卡住求助触发率 -> 求助后继续执行率 -> 即时主观改善`

### 3. 反思链

`反思打开率 -> 反思完成率 -> 即时主观改善 -> 次日闭环效应`

这样更容易让 reviewer 看出：

- scaffold 有没有进入真实流程
- scaffold 有没有在当下产生“可感知”的支持
- scaffold 是否可能对后续行为产生影响

---

## 最终建议

如果只保留一组最现实、最稳、最容易让 CHI reviewer 理解的定量指标，建议优先采用：

### Primary

1. `第一步建议使用率`
2. `卡住求助触发率`
3. `反思完成率`
4. `scaffold 后即时主观改善`

### Secondary

5. `第一步建议跳过率`
6. `求助后继续执行率`
7. `每日任务完成率`
8. `每日卡住次数`
9. `反思打开率`

### Exploratory

10. `反思平均回复字数`
11. `反思对话轮数`
12. `次日闭环效应`

这组指标的优点是：

- 当前原型基本都能支持
- 不依赖新增复杂功能
- 不依赖高主观性的人工判断
- 更贴近“元认知 scaffold 是否被接受和理解”
- 更适合与你的访谈和质性分析形成互证

8. `每日卡住次数`

### Exploratory

9. `次日闭环效应`

这组指标的优点是：

- 当前原型基本都能支持
- 不依赖新增复杂功能
- 不依赖高主观性的人工判断
- 适合做同一参与者的纵向分析
- 每个指标都能直接讲清楚其意义
# 研究问题与埋点方案

## 研究背景

研究方向：利用生成式 AI 帮助 ADHD 大学生提高元认知以改进任务管理。

当前原型的三个阶段：

1. `启动阶段` — 启动第一步
2. `执行阶段` — 任务过程中卡住求助
3. `反思阶段` — 数据可视化支持的反思

## 研究问题

- **RQ1**: What metacognitive challenges do university students with ADHD encounter during academic task planning, and how are these challenges expressed in how they define tasks, estimate duration, and determine priorities?
- **RQ2**: How does a GenAI-powered metacognitive scaffold that prompts reflection during planning (e.g., when decomposing tasks, estimating task duration, or setting priorities) shape the task-planning processes of university students with ADHD?
- **RQ3**: How does ongoing interaction with this GenAI-driven metacognitive scaffold influence the quality and structure of students' task plans and the metacognitive abilities during planning?

---

## RQ1：ADHD 大学生在任务规划中遇到哪些元认知挑战

核心关注：用户在没有或刚接触 scaffold 时如何定义任务、估计时长、决定优先级。

### 启动阶段

| 收集什么 | 埋点位置 |
|---------|---------|
| 用户输入的任务标题原文（是否模糊、是否过大、是否缺少边界） | 任务创建时记录原始文本 |
| 任务是否有子任务拆解，拆了几层，每层粒度 | 任务数据结构中已有子任务字段 |
| 是否设置了优先级，设置了什么 | 任务创建/编辑时记录 priority 变化 |
| 是否设置了预估时长（当前原型无此字段，建议新增） | 新增 `estimatedMinutes` 字段 |
| 从打开应用到开始第一个任务的时间差 | `app.opened` 事件 → 第一个 `session.started` 的时间差 |
| 用户是否修改了 AI 给的第一步建议 | 第一步建议展示 → 用户实际开始的动作对比 |

### 执行阶段

| 收集什么 | 埋点位置 |
|---------|---------|
| 实际执行时长 vs 预估时长 | `session.ended` 的 `totalDurationSeconds` vs `estimatedMinutes` |
| 任务切换频率与模式（频繁跳转 = 优先级不清楚） | 连续 `session.started` 中 `taskId` 变化序列 |
| 卡住频率与卡住原因分类 | 已有 stuck 相关 tracker events，可增加原因分类标签 |
| 任务完成率与完成顺序（是否符合设定的优先级） | 任务 `completed` 时间戳 vs priority 排序 |

### 反思阶段

| 收集什么 | 埋点位置 |
|---------|---------|
| 用户在反思中自述的困难（自然语言） | 反思对话中用户消息的文本 |
| 用户是否能准确回顾当天表现（对比实际数据 vs 用户自述） | 反思对话文本 + 当日 summary 数据 |
| 用户对自身问题的归因方式（归因于能力 / 任务 / 环境 / 方法） | 反思对话文本分析（编码） |

## RQ2：GenAI scaffold 如何影响用户的任务规划过程

核心关注：scaffold 的每次介入是否被理解、被使用、以及如何改变用户的下一步行为。

### 启动阶段

| 收集什么 | 埋点位置 |
|---------|---------|
| AI 第一步建议的内容 | `generateMicroActions` 返回值记录 |
| 用户对建议的响应：采纳 / 修改 / 忽略 / 跳过 | 新增事件 `firstStep.response` |
| 用户修改后的版本（如果修改了） | 记录用户实际输入的第一步文本 |
| 从看到建议到开始执行的延迟 | 建议展示时间戳 → `session.started` 时间戳 |
| Task Understanding 反思问题的回答内容 | 已有 `understandingContext`，确保完整记录 |

### 执行阶段

| 收集什么 | 埋点位置 |
|---------|---------|
| 用户是否主动触发卡住求助 | 已有 stuck 相关事件 |
| 触发时机：卡住多久后才求助 | 上一个有效操作 → stuck 触发的时间差 |
| AI 卡住预测是否命中（用户选了哪个选项 / 自己输入了别的） | 新增 `stuckChip.selected` / `stuckChip.customInput` 事件 |
| 绕路建议的采纳情况 | 新增 `pivot.response` 事件 |
| 求助后是否恢复执行、恢复用时 | stuck 事件 → 下一个 `session.started` 的时间差和任务 ID |
| 反思提示（StuckReflection）的查看与停留时长 | 新增 `stuckReflection.shown` + `stuckReflection.dismissed` 事件 |

### 反思阶段

| 收集什么 | 埋点位置 |
|---------|---------|
| 用户是否打开反思、打开时机 | 新增 `reflection.opened` 事件 |
| 反思对话的轮数与每轮字数 | 从 `reflection-{date}.json` 的 bubbles 统计 |
| 用户回答的深度（一两个字 vs 展开描述） | 用户消息的字符数 / 句数 |
| AI 反思问题是否引发了新的自我认识 | 反思对话文本（需人工编码） |
| 用户是否看了数据可视化、看了哪些图表 | 新增 `chart.viewed` 事件，记录图表 ID |
| 截图是否被包含在对话中 | 已有，`screenshotBase64` 是否非空 |
| 反思是否完成（到 step 4）还是中途退出 | 已有 `step` 字段 |

## RQ3：长期使用如何影响任务规划质量和元认知能力

核心关注：跨天/跨周的纵向变化，同一指标在不同时间点的对比。

### 启动阶段（纵向对比）

| 收集什么 | 对比维度 |
|---------|---------|
| 任务标题的具体程度是否随时间提高 | 第 1 天 vs 第 7 天 vs 第 14 天的任务文本粒度（编码） |
| 子任务拆解数量与质量变化 | 每日/每周统计子任务层级和数量 |
| 预估时长准确度变化（实际/预估比值） | 每日统计，绘制趋势 |
| AI 第一步建议的采纳率变化 | 每日 `firstStep.response` 统计 |
| 从打开到开始的启动延迟变化 | 每日统计，绘制趋势 |

### 执行阶段（纵向对比）

| 收集什么 | 对比维度 |
|---------|---------|
| 每日卡住次数变化 | 每日 stuck 事件计数 |
| 卡住后恢复时间变化 | 每日平均恢复时间 |
| 卡住求助的主动性变化（多久后才求助） | 每日平均触发延迟 |
| 任务完成率变化 | 每日/每周统计 |
| 心流时段占比变化 | 已有 `flowMinutes`，每日统计 |
| 任务切换频率变化 | 每日统计 |

### 反思阶段（纵向对比）

| 收集什么 | 对比维度 |
|---------|---------|
| 反思对话深度变化（轮数、字数、是否展开叙述） | 每日统计 |
| 反思完成率变化（是否到 step 4） | 每日统计 |
| 反思中出现的元认知表达变化（自我监控、自我评估、策略调整） | 文本编码，按周对比 |
| Commitment 的内容是否从泛泛变得具体 | Commitment Memory 文本编码 |
| Commitment 的落地率变化（说了是否做了） | 每日 commitment vs 次日行为对比 |
| 用户归因方式的变化（从"我不行"到"这类任务需要换方法"） | 反思文本编码，按周对比 |

## 建议新增的埋点事件汇总

当前原型已有的事件覆盖了执行层面的基础数据，但对 scaffold 交互过程和元认知表达的捕捉还不够。建议新增：

| 事件名 | 触发时机 | 关键字段 |
|-------|---------|---------|
| `app.opened` | 应用被打开/从后台恢复 | `timestamp` |
| `firstStep.shown` | AI 第一步建议展示给用户 | `taskId`, `suggestions[]` |
| `firstStep.response` | 用户对建议做出响应 | `taskId`, `action`: adopted / modified / skipped, `modifiedText?` |
| `stuckChip.selected` | 用户选择了 AI 预测的卡点 | `taskId`, `chipText` |
| `stuckChip.customInput` | 用户自己输入了卡住原因 | `taskId`, `inputText` |
| `pivot.response` | 用户对绕路建议的响应 | `taskId`, `action`: adopted / ignored |
| `stuckReflection.shown` | 反思提示卡片展示 | `taskId`, `timestamp` |
| `stuckReflection.dismissed` | 反思提示卡片关闭 | `taskId`, `viewDurationMs` |
| `reflection.opened` | 用户打开反思面板 | `date`, `timestamp` |
| `reflection.completed` | 反思对话到达 step 4 | `date`, `totalRounds`, `totalUserChars` |
| `chart.viewed` | 用户查看了某个图表 | `chartId`, `viewDurationMs` |

## RQ 与数据源的映射关系

```
RQ1（挑战是什么）
  ├── 任务原始文本 + 结构         ← 启动阶段
  ├── 执行偏差数据               ← 执行阶段
  └── 反思自述 + 归因             ← 反思阶段 + 访谈

RQ2（scaffold 如何影响过程）
  ├── AI 建议 + 用户响应          ← 启动阶段埋点
  ├── 卡住求助交互全链路          ← 执行阶段埋点
  └── 反思深度 + 数据使用         ← 反思阶段埋点

RQ3（长期变化）
  ├── 上述所有指标的纵向趋势      ← 按天/周聚合
  ├── 元认知表达编码变化          ← 反思文本纵向分析
  └── Memory 与行为闭环率        ← Commitment 落地追踪
```
